
# Wireshark Traffic Analysis

## Scope

- **Capture Point:** Server-VM (`192.168.152.40`)
- **Attacker:** Kali Linux (`192.168.152.20`)
- **Network:** VMware Host-only (`192.168.152.0/24`)
- **Tools:** Wireshark and tcpdump
- **Traffic Analyzed:** SSH brute-force attempts, Nmap reconnaissance, HTTP probes, and DNS traffic.

**Capture Architecture:** Traffic was captured directly on Server-VM because VMware VMnet2 is a host-only switch, not a hub. Network-Monitoring-VM (`.50`) cannot automatically capture traffic exchanged between Kali (`.20`) and Server-VM (`.40`).

## Capturing Traffic

Start packet capture on Server-VM during the simulated attacks.

**Identify network interface:**

```bash
ip a
```

**Start packet capture:**

```bash
sudo tcpdump -i ens33 -w capture.pcap host 192.168.152.20
```

Replace `ens33` with the actual interface connected to VMnet2.

Stop capture using `Ctrl+C`.

**Trim capture for documentation:**

```bash
mkdir -p wireshark

editcap -r capture.pcap wireshark/capture-trimmed.pcap 1-500
```

## 1. SSH Brute-Force Analysis

**Wireshark filter:**

```wireshark
tcp.port == 22 && ip.src == 192.168.152.20 && ip.dst == 192.168.152.40
```

**Analysis:**

- Identified repeated SSH connection attempts from Kali.
- Observed TCP three-way handshakes.
- Analyzed repeated connection and disconnection patterns.
- Correlated packet timestamps with Ubuntu `auth.log`.
- SSH authentication payloads remained encrypted.

**Key Observation:** Repeated short-lived SSH connections are consistent with automated password-guessing activity.

## 2. Nmap SYN Scan Analysis

**Filter A — All initial SYN packets:**

```wireshark
tcp.flags.syn == 1 && tcp.flags.ack == 0
```

**Filter B — SYN packets from Kali:**

```wireshark
tcp.flags.syn == 1 && tcp.flags.ack == 0 && ip.src == 192.168.152.20
```

**Analysis:**

- Identified SYN scan traffic originating from Kali.
- Examined destination ports and TCP response patterns.
- Identified open and closed port responses.
- Correlated network activity with Nmap scan results.

**Expected Observation:** SSH (22) and HTTP (80) respond with SYN/ACK if listening; closed ports typically respond with RST/ACK.

## 3. HTTP Service Detection

Nmap's `-sV` option sends application-level probes to identify running services.

**Wireshark filter:**

```wireshark
http && ip.src == 192.168.152.20
```

**Analysis:**

- Inspected HTTP GET requests generated during service detection.
- Examined User-Agent information.
- Reviewed Apache HTTP response headers.
- Compared service information with Nmap results.

**Key Observation:** HTTP requests generated by Nmap service detection can appear even when no user manually browses the website.

## 4. DNS Traffic Analysis

**Wireshark filter:**

```wireshark
dns && ip.addr == 192.168.152.20
```

**Analysis:**

- Checked for DNS queries originating from Kali.
- Investigated possible reverse-DNS lookups during Nmap reconnaissance.
- Compared captured DNS activity with the lab network configuration.

**Expected Observation:** Zero DNS packets if no resolver or DNS traffic is used during the capture. Nmap's `-n` option disables DNS resolution.

## Troubleshooting

- **No traffic visible:** Capture directly on Server-VM (`.40`).
- **Permission denied:** Run tcpdump using `sudo`.
- **Incorrect interface:** Verify the interface using `ip a`.
- **Empty capture:** Confirm Kali and Server-VM are connected to the same Host-only network.
- **No HTTP packets:** Verify Apache is running and Nmap service detection was performed.
- **No DNS packets:** Check whether DNS resolution was disabled or unnecessary.
